Summary概要

  • Problem. With LMCacheMPConnector, a burst of N waiting requests gets N LOOKUP RPCs in a single vLLM scheduler step. On the LMCache MP server, LOOKUP and the heartbeat PING share one request pool, so the PING times out and the scheduler adapter enters degraded mode, in which lookups checked report a miss and are recomputed.
  • Change. Lookups that have been submitted but not yet consumed are bounded by vLLM's max_num_seqs. A request beyond the bound returns (None, True), the existing vLLM signal for "ask me again next step", without sending a LOOKUP.
  • Scope. About 30 lines of production code in two files, no new config option, a design-doc update, and 5 new tests. The bound is off when lmcache.mp.eager_prefetch is enabled and for any caller that does not pass it.
  • Effect (one GPU, N = 8192). The median TTFT went from 39.0–43.7 s to 28.0–28.3 s, which equals vanilla vLLM. Degraded-mode entries went from 1 to 0.
  • 问题。使用 LMCacheMPConnector 时，若有 N 个请求同时进入等待队列，vLLM 会在一个调度步内发出 N 个 LOOKUP RPC。LMCache MP 服务端的 LOOKUP 与心跳 PING 共用同一个请求线程池，因此 PING 超时，调度端 adapter 进入降级模式（degraded mode）。在此期间被检查的 lookup 一律按未命中处理，需要重新计算。
  • 改动。已提交但尚未被消费的 lookup 数量受 vLLM 的 max_num_seqs 限制。超出上限的请求返回 (None, True)，即 vLLM 已有的“下一步再问我”信号，并且不发送 LOOKUP。
  • 范围。两个文件中约 30 行生产代码，没有新增配置项，更新一份设计文档，新增 5 个测试。启用 lmcache.mp.eager_prefetch 时，以及调用方未传入上限时，上限均不生效。
  • 效果（单 GPU，N = 8192）。TTFT 中位数从 39.0–43.7 秒降到 28.0–28.3 秒，与原生 vLLM 持平。进入降级模式的次数从 1 次降为 0 次。

Problem: one scheduler step looks up the whole waiting queue问题：一个调度步查询整个等待队列

vLLM v1's scheduler walks the waiting queue every step. For each request without computed tokens it asks the KV connector how many tokens are cached (get_num_new_matched_tokens). When the connector answers None ("not known yet"), the scheduler moves the request to a per-step skipped queue and continues. The skip does not consume token budget, and the loop stops only when the running batch is full or the budget is exhausted (vllm/v1/core/sched/scheduler.py, waiting loop, vLLM 0.24).

LMCacheMPConnector answers None while its asynchronous lookup is in flight, which is true for every request in its first poll. vLLM's waiting queue can hold far more requests than max_num_seqs, for example after a burst of arrivals or when clients keep more requests in flight than one instance can run. Whenever the running batch has room, a single scheduler step therefore submits a LOOKUP for every waiting request: the number of LOOKUPs follows the queue depth, not what vLLM can run.

On the server, lookup, query_prefetch_status, free_lookup_locks, end_session, and ping are all HandlerType.BLOCKING handlers in the NORMAL pool. That pool has --max-cpu-workers threads, which falls back to --max-workers (default 1). Each LOOKUP hashes the prompt, creates a session, and submits a prefetch, so thousands of them form a backlog of several seconds. The scheduler's heartbeat PING waits behind that backlog. If it gets no answer within heartbeat_interval (10 s), the adapter marks the server unhealthy. While it is unhealthy, check_lookup_result returns 0, so every request checked in that window is treated as a miss and recomputed. Recovery comes with the next successful PING, 10 s later.

vLLM v1 调度器每一步都会遍历等待队列。对每个尚无已计算 token 的请求，它会询问 KV connector 有多少 token 已被缓存（get_num_new_matched_tokens）。若 connector 返回 None（“暂时未知”），调度器把该请求移入本步的跳过队列，然后 continue。这次跳过不消耗 token 预算；只有当运行批次已满或预算耗尽时循环才会停止（vllm/v1/core/sched/scheduler.py 中的等待队列循环，vLLM 0.24）。

LMCacheMPConnector 在异步 lookup 进行期间返回 None，而每个请求的第一次轮询都处于这种状态。vLLM 的等待队列可以容纳远多于 max_num_seqs 的请求，例如请求突发到达之后，或客户端同时保持的请求数超过单个实例能运行的数量时。因此只要运行批次还有空位，一个调度步就会为所有等待中的请求提交 LOOKUP：LOOKUP 的数量取决于队列深度，而不是 vLLM 能运行多少请求。

在服务端，lookup、query_prefetch_status、free_lookup_locks、end_session 和 ping 都是 NORMAL 线程池中的 HandlerType.BLOCKING 处理函数。该线程池的线程数由 --max-cpu-workers 决定，未设置时沿用 --max-workers（默认 1）。每个 LOOKUP 都要计算 prompt 的哈希、创建 session 并提交 prefetch，数千个 LOOKUP 会积压成数秒的队列。调度端的心跳 PING 排在这批积压之后。若在 heartbeat_interval（10 秒）内收不到回应，adapter 就把服务端标记为不健康。不健康期间 check_lookup_result 返回 0，因此这段时间内被检查的请求都按未命中处理并重新计算。要等 10 秒后下一次 PING 成功才会恢复。

Design and alternatives设计与备选方案

What is bounded

The adapter already keeps self._lookups: dict[str, LookupState]. An entry is added when a LOOKUP is submitted and removed by cleanup_lookup_result. So len(self._lookups) is exactly the number of lookups that have been submitted but not yet consumed, and no new counter is needed. The bound is checked against that size.

Why the check lives in the connector, not inside maybe_submit_lookup_request

If maybe_submit_lookup_request silently refused, the next check_lookup_result would find no lookup for the request and return 0. That reads as a cache miss, so the request would be computed from scratch instead of deferred. The connector therefore asks can_submit_lookup first and returns (None, True). The method's docstring states that callers must check it first.

Why max_num_seqs

vLLM can run at most max_num_seqs requests, so in one step it can admit at most max_num_seqs − len(running) new ones. The bound is a heuristic, not a limit vLLM enforces: holding up to max_num_seqs unconsumed lookups gives a full batch of look-ahead, which keeps L2→L1 prefetch overlapping the queue wait, without letting the whole queue flood the server. It also reuses an existing engine setting, so no new option is introduced.

Why max_pending_lookups defaults to None (unbounded)

The adapter is also built by vLLM's in-tree fallback copy of the connector (vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py), which does not pass the new argument and never calls can_submit_lookup. With the default None, that path behaves exactly as before.

Why the bound is off under lmcache.mp.eager_prefetch

Eager prefetch (opt-in, off by default) submits a lookup in on_new_request when a request is enqueued. That path is deliberately not gated: the user chose early lookups. With the bound active as well, eager lookups would fill it, and any request that still needs a scheduler-time lookup could be refused for as long as the backlog stays at or above max_num_seqs. That covers preempted requests (their first lookup was already consumed), resumable requests (skipped by on_new_request), and requests that arrived while the server was unhealthy. So the connector passes None in this mode, which keeps eager behavior unchanged.

限制的对象

adapter 本来就维护 self._lookups: dict[str, LookupState]。提交 LOOKUP 时加入一项，cleanup_lookup_result 时删除。因此 len(self._lookups) 恰好等于“已提交但尚未被消费”的 lookup 数量，不需要新增计数器。上限就是针对这个大小来检查的。

为什么检查放在 connector，而不是 maybe_submit_lookup_request 内部

如果 maybe_submit_lookup_request 静默拒绝，下一次 check_lookup_result 找不到该请求的 lookup，会返回 0。这会被当作缓存未命中，请求会被从头计算，而不是延后。因此 connector 先调用 can_submit_lookup，没有空位时返回 (None, True)。该方法的 docstring 写明了调用方必须先做这项检查。

为什么选 max_num_seqs

vLLM 最多同时运行 max_num_seqs 个请求，因此一步最多接纳 max_num_seqs − len(running) 个新请求。这个上限是一种经验取值，并非 vLLM 自身强制的限制：保留最多 max_num_seqs 个未消费的 lookup，相当于提前准备一整批，让 L2→L1 prefetch 仍能与排队等待重叠，同时又不会让整个队列压垮服务端。它复用了现有的引擎配置，因此无需新增配置项。

为什么 max_pending_lookups 默认为 None（不限制）

vLLM 仓库内自带的后备版 connector（vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py）也会构造这个 adapter。它不传新参数，也不调用 can_submit_lookup。默认值为 None 时，这条路径的行为与以前完全相同。

为什么启用 lmcache.mp.eager_prefetch 时关闭上限

eager prefetch（需手动开启，默认关闭）会在请求入队时于 on_new_request 中提交 lookup。这条路径刻意不受上限约束，因为用户主动选择了提前 lookup。如果同时启用上限，eager lookup 会把上限占满；只要积压不低于 max_num_seqs，仍需要在调度时 lookup 的请求就可能一直被拒绝。这包括被抢占的请求（它们的第一次 lookup 已被消费）、可恢复（resumable）的请求（on_new_request 会跳过它们），以及服务端不健康期间到达的请求。因此在该模式下 connector 传入 None，eager 的行为保持不变。

考虑过的备选方案

备选方案本 PR 不采用的原因
为 PING 单独设置线程池，或提高其优先级只能缓解症状（心跳饥饿），无法消除浪费的工作。调度端仍会为几分钟后才运行的请求发出数千个 LOOKUP、加锁并 prefetch。两种修复互为补充；本 PR 是客户端这一半，不改动服务端或传输层代码。
在 maybe_submit_lookup_request 内部施加上限被拒绝的提交会变成“未命中”（见上文）。
为上限新增配置项目前没有具体需求；max_num_seqs 已经表达了 vLLM 能同时运行多少请求。编码规范要求不添加推测性的配置项。
使用更小的固定上限（如 64）排队的 LOOKUP 更少，但提前量也更小。一步中被接纳的请求更可能发现自己的 lookup 尚未开始，从而推迟 prefetch。

2. can_submit_lookup: the admission rule准入规则 vllm_multi_process_adapter.py:715

+   def can_submit_lookup(self, request_id: str) -> bool:
+       ...
+       return (

There are three clauses:

  1. No bound configured: always admit. This is the legacy and eager-prefetch behavior.
  2. Request already has a lookup: always admit. The scheduler polls the same request every step until it is allocated. Refusing it would hide a result that has already been paid for, and the request would never leave the bound, which is a self-inflicted stall.
  3. Otherwise: admit only while there is room.

The method is pure: it reads state and has no side effects. Everything runs on the scheduler thread, like the rest of the per-request dict (see docs/design/integration/vllm/mp_lookup_state.md, "Threading").

共有三个条件：

  1. 未配置上限：总是允许。这是旧行为，也是 eager prefetch 的行为。
  2. 请求已有 lookup：总是允许。在被分配 block 之前，调度器每一步都会轮询同一个请求。若拒绝它，已经付出代价得到的结果会被藏起来，而这个请求也永远不会离开上限，等于自己把自己卡死。
  3. 其他情况：只在有空位时允许。

该方法是纯函数：只读状态，没有副作用。它与该请求字典的其他操作一样都在调度线程上执行（见 docs/design/integration/vllm/mp_lookup_state.md 的 “Threading” 一节）。

Where the gate sits matters:

  • After the two early returns for BYPASS_LMCACHE and for the failed-async-load reset. Those return 0 and must keep working when the bound is full.
  • Before any state is written. lookup_started_at stays unset, so lookup-latency stats measure from the real submission. apc_covered_tokens is not frozen either, so the APC boundary is taken at the real submit. The tracker stays in its initial state, and the next poll repeats the same checks.
  • (None, True) is the value this method already returns while a lookup is in flight, so vLLM's handling is unchanged: skip without consuming budget, then poll again next step.

Other submit sites are intentionally not gated. The APC-shrink re-lookup (:1506) calls cleanup_lookup_result right before resubmitting, so the count does not change. on_new_request (:1566) only submits under eager prefetch, where the bound is None.

The docstring of get_num_new_matched_tokens gains a note that None is also returned, with no lookup submitted, while the bound is full.

检查放在哪里很关键：

  • 放在 BYPASS_LMCACHE 和“异步加载失败后重置”这两个提前返回之后。它们返回 0，在上限已满时也必须照常工作。

Why the bound cannot leak or stall (default configuration)为什么上限不会泄漏或卡死（默认配置）

A stall would need the bound to be full of entries that are never cleaned up. These are all the places that add to or remove from _lookups:

Entries can be held for a while by requests whose lookups are resolved but which cannot be admitted yet, for example because KV blocks are short, the LoRA limit is reached, or the token budget is used up. That is backpressure, not a deadlock. Those are exactly the requests that run next, and vLLM admits them as running requests finish.

如果某些请求的 lookup 已完成但暂时无法被接纳（例如 KV block 不足、达到 LoRA 上限或 token 预算用完），它们会暂时占住空位。这是背压而不是死锁：这些请求正是下一批要运行的请求，随着运行中的请求结束，vLLM 会接纳它们。

Compatibility, risks, known gaps兼容性、风险与已知不足

  • Compatibility. The adapter argument is keyword-only with a None default, so vLLM's in-tree fallback connector keeps its old behavior. No config, wire format, or server change. The bound is off under lmcache.mp.eager_prefetch.
  • Known limitation: PRIORITY scheduling policy should-fix candidate. While the bound is full, a high-priority request that is deferred early in a step can lose a freed slot to a lower-priority request polled later in the same step. It never deadlocks, and FCFS (the default) is unaffected because the oldest deferred request is also the first one polled. It only matters when lookups, not compute or memory, are the bottleneck and the backlog exceeds max_num_seqs. A possible follow-up: once one request is deferred in a step, defer all new lookups for the rest of that step.
  • Partial protection. A cold burst still sends up to max_num_seqs LOOKUPs in one step ahead of the PING. The bound reduces heartbeat starvation; it does not remove it. A separate PING pool would be the server-side complement.
  • Eager prefetch keeps the old unbounded behavior, including its exposure to bursts.
  • TP > 1 not measured. LOOKUP count is per request, not per rank. But server-side work per lookup grows with the number of KV ranks (one key row per object group and KV rank), and each worker rank also sends its own PING through the same pool, so the effect is expected to be larger at high TP.
  • Stats. Lookup latency (record_lookup) starts at submission, so time spent deferred is not counted.
  • 兼容性。adapter 的新参数为仅限关键字参数且默认为 None，vLLM 仓库内的后备 connector 行为不变。没有修改配置、通信格式或服务端。启用 lmcache.mp.eager_prefetch 时上限不生效。
  • 已知限制：PRIORITY 调度策略 可作为后续修复。上限已满时，一个在本步较早被延后的高优先级请求，可能被同一步中较晚轮询到的低优先级请求抢走刚释放的空位。这不会造成死锁；默认的 FCFS 不受影响，因为最早被延后的请求也是最先被轮询的。只有当瓶颈在 lookup 而不在计算或显存，并且积压超过 max_num_seqs 时才有影响。可能的后续修复：一旦某个请求在本步被延后，本步余下的新 lookup 全部延后。
  • 只是部分缓解。冷启动突发时，一步中仍可能有最多 max_num_seqs 个 LOOKUP 排在 PING 之前。上限减轻了心跳饥饿，但没有彻底消除。为 PING 单独设置线程池是服务端的补充方案。
  • eager prefetch 保持旧的不限制行为，因此仍会受到突发的影响。
  • 未测量 TP > 1。LOOKUP 的数量按请求计，与 rank 数无关。但服务端每个 lookup 的工作量随 KV rank 数增长（每个 object group 和 KV rank 一行 key），而且每个 worker rank 也会通过同一个线程池发送自己的 PING，因此在高 TP 下影响预计会更大。
  • 统计。lookup 延迟（record_lookup）从提交时开始计时，被延后的时间不计入。
